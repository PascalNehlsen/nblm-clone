# Security

How this app handles the risks of an LLM application. The mapping to the OWASP Top 10 for LLM Applications comes with the chat PR (D); the rules themselves are in AGENTS.md ("Hard rules: AI and data security").

To report a vulnerability, open a private security advisory on GitHub.

## Accepted risks

| Risk | Why accepted | Bounded by | Since |
|---|---|---|---|
| A user can insert fake `assistant` messages into their own chat history through PostgREST | The server writes messages with the user's login, so RLS guards every write; a separate writer role would bypass RLS ([ADR 0004](docs/adr/0004-sources-chunks-messages.md)) | History is per user, so only the forger sees them; rendering rules apply to every message (no raw HTML, no remote content, links http(s) only); a forged row never reaches the model as a source. If PR D sends chat history to the model, forged rows reach it as the forger's own conversation context, in their own session and on their own budget; PR D decides whether history comes only from rows it wrote | PR A1 |
| An editor can insert chunks directly through PostgREST, bypassing ingestion: no upload size limit, no magic-byte check, and an embedding that need not match the text, so a chunk can be retrieved for any question | Ingestion writes chunks with the user's login | Only owners and editors of that notebook, never viewers, strangers or anonymous users; `content` is capped at 8,000 characters; the 20,000-chunk cap per notebook is enforced in the database by a statement-level trigger (PR C1, `private.enforce_notebook_chunk_limit`), not only in ingestion code. A planted chunk affects only that notebook's answers, which the editor could already shape through their sources | PR A1 |
| Members, including anonymous demo users, can insert messages and citations in a loop without a model call. Many citations to one chunk also slow down deleting that source (one foreign key update and two trigger calls per citation) and could push the deletion past the statement timeout | Messages and citations are written with the user's login; the budget check guards model calls, not inserts | `content` is capped at 20,000 characters, quotes at 2,000, citations at 20 per message; history is per user; the number of messages is not capped yet: a per-user insert rate limit covering messages and citations is open for PR E or F | PR A1 |
| A user can insert citations with arbitrary quotes for their own messages through PostgREST | Same as fake assistant messages: the server writes citations with the user's login | Only for the user's own messages, only chunks of the same notebook (foreign key), quotes capped at 2,000 characters; PR D validates citations server-side when it writes them | PR A1 |
| A signed URL for a source file keeps serving the file until it expires, even after the source row is deleted or the member is removed (measured on storage-api v1.79.28) | Signed URLs are bearer tokens checked only when they are issued | Only members can create them; PR C keeps expiries short (seconds, for one download) or proxies downloads through the server, with a test | PR A2 |
| The daily budget and the kill switch are enforced only on the server: a client that reaches the model provider without the server would not be counted | Model calls happen only on the server (the chat model has no tools, model config is server-side), and only the server can write usage: `reserve_model_call` and `settle_model_call` are executable by `service_role` alone, so no user can reserve, settle or reset their own costs ([ADR 0006](docs/adr/0006-model-budget-and-kill-switch.md)) | The `service_role` secret key, which bypasses RLS everywhere, is confined to one module under `lib/server/admin/` that exports only `reserve` and `settle`, imported only by the model-call wrapper `lib/server/model/call.ts`: `eslint.config.mjs` bans static imports and re-exports of it everywhere else (`tests/unit/eslint-imports.test.ts`), and a source scan in `tests/unit/auth-boundary.test.ts` also catches dynamic `import()` and `require()` with a literal specifier, which ESLint does not see (a specifier built at runtime, such as a template literal, gets past both); the module surface and the key allowlist (secret key or `service_role` JWT only) are tested in `tests/unit/admin/usage.test.ts`; it is not set in Vercel Preview, so previews fail closed; even `service_role` can insert only reservation columns and settle each row once | PR E1 |
| A signed upload URL for a source path is a bearer token: whoever holds it can upload to that one path until it expires (2 hours per the Supabase Storage docs, not measured here) | The browser uploads PDFs straight to Storage, because Vercel caps request bodies at 4.5 MB and streaming through the server is ruled out | Issued only after the source row exists, by Storage under the object insert policy (owners and editors, never anonymous users); one path only; no upsert, so an existing object cannot be overwritten (measured locally: the URL is refused for a path that already has an object); the server then checks the bytes by content (magic bytes) and size before any extraction ([ADR 0007](docs/adr/0007-ingestion-pipeline.md)). **Not bounded yet:** the token is checked only when it is issued. Measured locally (2026-10-19): after the source row is deleted, an upload with the old token is still accepted, and the object is then invisible to every user and counted by no cap. An editor can repeat create, delete, upload to grow storage, and a slow upload can land after a co-editor deleted the source. Until the C4 sweep removes objects without a source row, only the 20 MB per object and the project's storage quota bound this | PR C1 |
| The server parses untrusted PDFs with pdf.js (`unpdf` 1.8.1, which bundles pdf.js 6.1.200) | Extracting text needs a parser; pdf.js is the maintained one | Text only, no rendering, no fonts; the bundled pdf.js has no eval path (the CVE-2024-4367 class), and `isEvalSupported: false` is passed anyway; at most 20 MB, 500 pages and a 60 s deadline per file; library errors become fixed categories, never logged text | PR C1 |
| The server fetches web pages at URLs that owners and editors choose (URL import) | Importing a web page needs a server-side fetch; the browser cannot fetch other sites for us | Through the SSRF guard only ([ADR 0008](docs/adr/0008-ssrf-guard.md)): http(s), default ports, no credentials; every hop resolved and checked against blocked private, loopback, link-local, metadata, CGNAT, multicast and IPv6 special ranges, then connected to exactly the checked address; at most 5 redirects, no https to http; 20 s and 5 MB per fetch; HTML or plain text only. Not anonymous users, not viewers; at most 50 sources per notebook. **Not bounded yet:** no per-user rate limit on imports, so an editor can make the app send GETs to public hosts of their choice from Vercel's addresses | PR C2 |
| Untrusted HTML is turned into text by our own scanner | No dependency, no script engine | A linear single-pass scanner: no code runs, no remote loads, attributes are dropped; a misparse costs quality, not safety; at most 5 MB in and 300,000 characters out | PR C2 |
| Rows of kind `url` inserted through PostgREST before C2 may have no `source_url` | The check `sources_url_has_source_url` is `NOT VALID` so the migration cannot fail on such rows | New inserts and every update are checked, so such a row cannot be claimed (the status update fails the check): it stays `pending` with no fetch and can only be deleted | PR C2 |
| An editor can fill a notebook with up to 50 sources of 20 MB each | Owners and editors add sources by design | At most 50 sources per notebook (DB trigger, PR C1) and 20 MB per file (bucket limit); viewers, strangers and anonymous users cannot add sources. The cap counts source rows, not objects: uploads through a token kept after deleting its source (row above) are not counted until the C4 sweep exists | PR C1 |
