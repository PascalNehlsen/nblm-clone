# Postmortem: game day, release rollback after a failed live smoke (2026-10-20)

- Type: planned game day ([ADR 0025](../adr/0025-game-day-fault-switch.md), runbook [game-day.md](../runbooks/game-day.md))
- Release run: v1.0.5, run 39413252457 (red by design)
- Impact: `https://app.sec-nblm.dev/login` answered 500 for 43 seconds (11:13:28 to 11:14:11 UTC). Logged-out visitors could not sign in; signed-in pages kept working. No data was touched
- Detection and recovery: automatic (live smoke, then rollback in `release.yml`); nobody intervened

## What we wanted to know

Does the release pipeline catch a fault that only shows on the live domain after promote, and does it restore the previous deployment by itself? The rollback path had never run for real.

## Setup

v1.0.4 (commit 3ee9ce5) was live and healthy. Pascal set `GAME_DAY_FAULT=live-login` in Vercel `nblm-web` (Production only, no redeploy) and tagged v1.0.5 on the same commit. With the variable set, a new deployment answers `/login` on `app.sec-nblm.dev` with 500, and only there.

## What worked

- The fault got past every check that does not use the domain (staged smoke, canary), as a real domain-only fault would.
- The live smoke caught it, and the rollback restored the recorded deployment in 4 seconds, with no human step.
- The run stays red, so a rolled-back release cannot pass as a success. The log line gave an exact timeline without any request data.

## What we learned and will change

- **Most of the outage is the smoke's retry backoff** (38 of 43 seconds). The retries exist for the window right after promote, when the domain can still serve the old deployment (#60). For a 5xx right after promote, fewer retries would cut the outage, at the cost of more false rollbacks. The current trade-off stays for now, and the number is recorded here.
- **A Redeploy in Vercel while the variable is set would break live with no rollback**, because it bypasses the release workflow. The runbook warns about this. A check in the live smoke for leftover game day variables is not possible without Vercel API access in that step, so this stays a runbook rule.
- **The fault covers one path.** A fault in an API route or a slow response would not be caught by the live smoke, which only checks `/login`. A broader live smoke (one authenticated page, the chat endpoint) is a candidate for v1.1.

## Follow-ups

- Repeat after any change to `release.yml` or `scripts/smoke.mjs`, and before the lead dev interview.
